# ルールの棚卸し

**このセッションは無人で走る。ユーザーに質問してはならない。**
判断できない事態に遭遇したら、何もせず INCIDENTS に `sig:"routine_blocked"` を記録して終える。

`.claude/rules/00-core.md` を書き換えてよいのは、この手順の中だけ。

目的は「良いルールを増やす」ことではなく、**ルールが文章のまま居座らないようにする**こと。
文章 → 機械の検査 → 文章から削除、の一方通行しか通らないようにしてある。
だから CLAUDE.md とルール集は、放っておいても増え続けない。

## 1. 失敗を集計する

`.claude/state/INCIDENTS.jsonl` を直近30日で `sig` ごとに数える。

## 2. ルールを足す（1回につき最大1件）

足す条件は次のどちらか。満たすものが無ければ**何も足さない。**

- 同じ `sig` が30日で3回以上
- `sev` が2以上のものが2回以上

足す前に、`00-core.md` の active を**全件読む**。
同じ場面（`trigger`）を扱うルールが既にあるなら、新規に足さず既存を書き直す。
矛盾したルールが2本並ぶと、どちらも守られなくなる。

新しいルールには必ず `review`（賞味期限、90日後）と `baseline`（導入前30日の発生回数）を書く。
`baseline` が無いと、後で効果を判定できず、退役させる根拠を失う。

**このリポジトリはセッションが週に数回しかない。** 30日3回という条件は、
偶然では滅多に満たされない代わりに、本当に繰り返している失敗だけを拾う。
サンプルが少ないので、`baseline` と `after` の比較は「傾向」以上には読まないこと。
迷ったら足さない。ルールは少ないほうが守られる。

## 3. ルールを退役させる

active 全件について、上から順に当てはめる。**当てはまった時点で処理して次へ。**

| 状態 | すること |
|---|---|
| `check` があり、`after` が 0 | 機械が見ている。文章は役目を終えた。**削除して ARCHIVE.md へ** |
| `review` を過ぎていて `hits` が 0 | 起きない問題への備え。**退役** |
| `review` を過ぎていて `after` < `baseline` | 効いている。`review` を90日延ばす。同時に機械で検査できないか1回考え、できるなら `tools/check_site.py` に足して文章を消す |
| `review` を過ぎていて `after` >= `baseline` | 文章では直らない。**文章を消し**、機械化の作業を NOW.md の「次の一手」に積む |
| active が20件を超えている | `hits` が最も少なく `review` が最も古い1件を**強制退役** |

どの枝を通っても、文章は消える方向にしか動かない。これが意図した設計。

## 4. 検査して push する

```bash
python3 tools/check_site.py --rules
```

ERROR を残さない。通ったらコミットして push する。

`.claude/` を変更した PR は自動マージされない。`needs-human` が付いて止まる。
**これは正しい動作。** 機械が自分を縛るルールを勝手に緩められないようにしてある。
止まったこと自体を失敗として記録しない。

## 5. NOW.md を更新して終える

「直近の決定」に、足したルール・退役させたルールを1行残す。
